# SciForge v0.2 — Retrieval and Citation Verification Engine

v0.2 is the first runnable SciForge release. It is deliberately narrow: it
**retrieves** bibliographic records from PubMed and Crossref, **deduplicates**
them, and **verifies** that each record's DOI / PMID resolves to matching
metadata. It does **not** draw conclusions, extract evidence, call a language
model (no xAI integration yet), or provide a web UI.

## 1. Usage

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

export SCIFORGE_CONTACT_EMAIL="you@example.org"   # recommended
export NCBI_API_KEY="your-key-here"               # optional

sciforge investigate "platelet activation under shear stress" \
    --max-results 20 --from-year 2015 --to-year 2025 --output-dir runs/
# equivalently: python -m sciforge investigate "..."
```

| Option | Default | Meaning |
|---|---|---|
| `question` | required | Research question; always searched **verbatim**, plus rule-based focused queries (see below) |
| `--max-results` | 20 | Maximum records requested from **each** source (1–1000) |
| `--from-year` / `--to-year` | none | Inclusive publication-year bounds (either may be omitted) |
| `--output-dir` | `runs/` | Parent directory for run folders (`runs/` is gitignored) |
| `-v/--verbose` | off | Log requests and errors to stderr (secrets redacted) |

Exit codes: `0` run completed (errors, if any, are recorded in the outputs);
`2` invalid arguments or configuration; `3` every database search failed.

**Query generation:** deterministic, rule-based expansion
(`query_expansion.py`, no model call). Query `q1` is always the research
question text as-is (PubMed `term`, Crossref `query.bibliographic`). Keywords
are extracted (stopwords, numbers, DOIs/PMIDs/URLs/emails removed) and matched
against a small curated concept map (anchor `platelet activation`; facets
`shear stress`/`shear-induced`, `mechanotransduction`, `platelet membrane`,
`membrane lipids`/`phospholipids`, `phosphatidylserine`, `lipid signaling`).
Each matched facet yields one focused query anchor AND facet — PubMed as
`"platelet activation"[tiab] AND ("shear stress"[tiab] OR "shear-induced"[tiab])`,
Crossref as plain words. At most 6 focused queries (7 total), deterministic
order, deduplicated. Queries only: no findings, citations or metadata are
generated. Per database, results are interleaved by rank, a record already
contributed by an earlier query (same PMID/DOI id) is skipped, and the list is
capped at `--max-results`; then the unchanged deduplication and verification
run. The plan (queries, concept ids, per-query result counts) is written to
`search_log.json` and `summary.json` under `query_expansion`. Disable with
`--no-query-expansion` or `SCIFORGE_QUERY_EXPANSION=false` (one query per
database, as before). Note: every extra query costs one more search round per
database.

## 2. Architecture

```
cli.py ── argparse, prints human summary
  └─ pipeline.py ── run_investigation(): orchestrates one run, writes files
       ├─ pubmed.py    PubMedClient   esearch → esummary; PMID lookups (batched)
       ├─ crossref.py  CrossrefClient /works search; /works/{doi} lookups
       ├─ dedup.py     conservative duplicate detection + merge with provenance
       ├─ verify.py    field comparison + status rules
       ├─ http_utils.py HttpFetcher (retries, backoff, JSON decoding), RateLimiter
       ├─ logging_utils.py RunLog, redaction helpers, UTC timestamps
       ├─ normalize.py DOI / PMID / title / surname normalization (pure functions)
       ├─ models.py    pydantic models (Record, Provenance, ErrorEntry, ...)
       └─ config.py    Settings from environment variables
```

All HTTP goes through one injectable `httpx.Client`, so tests substitute an
`httpx.MockTransport` and never touch the network.

## 3. Data flow

1. **PubMed search** — `esearch.fcgi` (`db=pubmed`, `retmode=json`, `term`,
   `retmax`; with year bounds also `datetype=pdat`, `mindate`, `maxdate`).
   NCBI requires both bounds, so an open bound is sent as `1800` or `3000`.
   Then `esummary.fcgi` (`retmode=json`, up to 200 IDs per request). Every
   E-utilities request carries `tool=sciforge`, plus `email` and `api_key`
   when configured.
2. **Crossref search** — `GET https://api.crossref.org/works?query.bibliographic=…&rows=N`,
   with `filter=from-pub-date:YYYY,until-pub-date:YYYY` when years are given
   and `mailto` when an email is configured.
3. **Normalization** into `Record` objects (see §6).
4. **Deduplication** (see §7). PubMed records come first, so they are the
   "primary" side of cross-source merges.
5. **Verification** of every unique record (see §8): all PMIDs are resolved
   with batched `esummary` calls; each distinct DOI with
   `GET /works/{doi}` on Crossref.
6. **Output** files are written and a short summary is printed.

Every request sends `User-Agent: SciForge/0.2.0 (https://github.com/SaraSheikhlary/sciforge-open; mailto:…)`;
the `mailto:` part is included only when `SCIFORGE_CONTACT_EMAIL` is set.

## 4. Configuration (environment variables only)

| Variable | Default | Purpose |
|---|---|---|
| `NCBI_API_KEY` | unset | Optional. Raises the PubMed throttle from 3 to 10 requests/s |
| `SCIFORGE_CONTACT_EMAIL` | unset | Recommended. Sent as NCBI `email`, Crossref `mailto`, and in the User-Agent |
| `SCIFORGE_TIMEOUT_SECONDS` | `20` | Per-request timeout (0.1–300) |
| `SCIFORGE_MAX_RETRIES` | `2` | Retries after the first attempt (0–5) |
| `SCIFORGE_BACKOFF_SECONDS` | `1` | Exponential backoff base (0–60) |
| `SCIFORGE_QUERY_EXPANSION` | `true` | Rule-based query expansion (`false` = question only) |
| `XAI_API_KEY` | — | Reserved for v0.3+; **not used** by v0.2 |

SciForge does not read `.env` files itself. Copy `.env.example` to `.env`
(gitignored) and export it, e.g. `set -a; source .env; set +a`.

Throttling: PubMed ≥0.34 s between requests without a key (≥0.11 s with a
key); Crossref ≥0.2 s (≥0.1 s with a contact email). Each database has its own
limiter, applied to every attempt including retries. Requests are strictly
sequential: SciForge uses no threads, async tasks, or connection concurrency,
so at most one request is in flight at a time.

Crossref etiquette: when `SCIFORGE_CONTACT_EMAIL` is set, every Crossref
request (search and DOI verification) carries `mailto=<email>` and the
User-Agent includes `mailto:<email>`; when unset, both are omitted. NCBI
requests carry `tool=sciforge`, plus `email` / `api_key` only when set.

## 5. Output files

Each run writes `runs/<UTC timestamp>/` (e.g. `runs/20260928T234100Z/`; a
`-1`, `-2`, … suffix is added if the folder exists):

| File | Contents |
|---|---|
| `search_log.json` | Every HTTP request: database, stage (`search` / `summary` / `verification`), query, URL, parameters (secrets redacted), timestamp, HTTP status, status (`ok` / `not_found` / `error`), attempts, result count, error type and message. Also the full list of error entries. |
| `sources.json` | Deduplicated records: `record_id`, `title`, `authors`, `year`, `doi`, `pmid`, `journal`, `source_database`, `source_url`, `retrieval_timestamp`, `provenance` (every contributing source record and the dedup rule that matched it), `conflicts`. |
| `verification.json` | One result per record: overall `status`, `reasons`, and per-identifier `checks` (identifier type/value, database, lookup outcome, HTTP status, error, and per-field comparisons with values and similarity). |
| `summary.json` | Question, query used, version, parameters, start/end times (UTC), per-source search status, hits reported, records retrieved per source, unique records, duplicates merged, verification counts by status, error count, failed / partially failed databases. |

All timestamps are ISO 8601 UTC (`2026-09-28T23:41:00Z`).

## 6. Record normalization

* Missing fields are `null` (authors: `[]`). **Nothing is guessed or filled in.**
* **DOI**: URL-decoded, whitespace stripped, prefixes such as
  `https://doi.org/`, `http://dx.doi.org/`, `doi:`, `DOI ` removed, trailing
  `.,;:` and quotes removed, lowercased; must match `10.<digits>/<suffix>`
  with no whitespace, otherwise `null`.
* **PMID**: accepts `123`, `" 123 "`, `"PMID: 123"`; must be 1–9 digits and
  non-zero; leading zeros removed; anything else is `null`.
* **Year**: PubMed — leading four digits of `pubdate`, else of
  `sortpubdate`; Crossref — first element of `issued`, then `published`,
  `published-print`, `published-online` `date-parts`. Must be an integer
  between 1500 and 2100, else `null`.
* **Authors**: PubMed entries with `authtype == "Author"` as given
  (`"Smith JA"`); Crossref person authors as `"Family, Given"`. Collective /
  organisational authors are excluded in both.
* **Journal**: PubMed `fulljournalname` (else `source`); Crossref first
  `container-title`.
* **DOI in PubMed**: from `articleids` entries with `idtype == "doi"`.
* **record_id**: `rec_` + 16 hex chars of SHA-256 over source database + DOI
  (else PMID, else normalized title, year, first-author surname, URL). Stable
  across runs.

## 7. Deduplication rules

Records are compared in order; each is merged into the first earlier record it
matches.

1. **Both have a DOI** → duplicates iff the normalized DOIs are equal.
   Different DOIs are never merged, even with identical titles.
2. **Both have a PMID** → duplicates iff equal; different PMIDs never merge.
3. **Fallback** (a DOI is missing on at least one side): merge only if the
   normalized title is identical (NFKD, accents removed, casefolded, markup
   and punctuation stripped, whitespace collapsed) **and** the year is
   identical **and** the normalized first-author surname is identical. If any
   of these is missing on either side, the records are **not** merged.
   Near-matches (e.g. one word different) are not merged.

Merging keeps the first record's non-null values and fills its null fields
from the second. Disagreements (title, year, DOI, PMID, journal, first author,
author count) are kept as human-readable strings in `conflicts`; differences
that vanish after normalization (e.g. letter case) are not reported. The
second record's provenance is appended with `matched_on` set to the rule used.

## 8. Verification rules

For each unique record, the DOI (if any) is resolved on Crossref and the PMID
(if any) on PubMed. The returned metadata is compared with the record:

| Field | Rule | Affects status |
|---|---|---|
| title | normalized exact match, or `difflib.SequenceMatcher` ratio **≥ 0.9** on normalized titles | yes |
| year | exact integer match | yes, if known on both sides |
| first author | exact match of normalized surnames | yes, if known on both sides |
| journal | normalized equal, one contains the other, or ratio ≥ 0.8 | **no** (soft, reported only) |

Fields missing on either side are `not_compared`.

**Per identifier**

* `verified` — the identifier resolved AND title = match AND year ≠ mismatch
  AND first author ≠ mismatch.
* `partially_verified` — resolved, but title mismatches or cannot be compared,
  or year / first author mismatches.
* `not_verified` — did not resolve: `not_found` (Crossref HTTP 404; or
  PubMed esummary succeeded but returned no document / an error document for
  the PMID) or `lookup_failed` (timeout, connection error, HTTP error,
  malformed response). A PubMed endpoint HTTP 404 is treated as
  `lookup_failed`, since it says nothing about the PMID.

**Per record** (combining DOI and PMID)

* No identifier → `not_verified`, reason `no_identifier`.
* No identifier resolved → `not_verified`, first reason `lookup_failed` if any
  lookup failed, else `not_found`.
* Otherwise `verified` if every resolved check is `verified` and no identifier
  was `not_found`. A lookup failure of the other identifier is listed in
  `reasons` but does not downgrade. Everything else is `partially_verified`
  (e.g. DOI verified but PMID not found, or the PubMed year disagrees).

Reasons are prefixed with the identifier type, e.g. `doi:year_mismatch`,
`pmid:not_found`.

## 9. Failure handling

No network or API problem aborts a run.

* **Retries:** 429, 5xx, timeouts, and connection/transport errors are retried
  up to `SCIFORGE_MAX_RETRIES` (default 2) times with backoff
  `SCIFORGE_BACKOFF_SECONDS × 2^attempt` (1 s, 2 s by default). If a retried
  response (429 or 5xx) carries a `Retry-After` header, that delay is used
  instead, in either RFC 9110 form: delay-seconds (`120`) or an HTTP-date
  (`Wed, 21 Oct 2026 07:28:00 GMT`). It is clamped to 0–30 s; an unparseable
  value falls back to exponential backoff. 404 and other
  4xx responses are not retried.
* **Recorded, then continue:** invalid JSON, missing keys, wrong types, NCBI
  error bodies, and malformed individual items (skipped, others kept).
* **Error entries** (in `search_log.json`) contain `database`, `stage`,
  `query`, `timestamp`, `error_type` (`timeout`, `connection_error`,
  `transport_error`, `rate_limited`, `http_error`, `not_found`,
  `invalid_json`, `unexpected_structure`, `missing_summary`,
  `unexpected_error`), `http_status` when available, a human-readable
  `message`, and the redacted URL.
* A DOI lookup returning 404 during verification is a normal outcome
  (`not_found` in `verification.json`), not an error entry.
* If one database fails, the other still runs and its records are still
  verified. `summary.json` lists `failed_databases` and
  `partially_failed_databases`.

## 10. Security

* Credentials come only from environment variables; `Settings.__repr__` hides
  them.
* `api_key`, `email`, and `mailto` values are replaced with `[REDACTED]` in
  logged parameters, URLs, error messages, and log lines, and every output
  file is scrubbed for the literal key/email values before it is written.
  (The email is not a secret, but it is personal data and is not needed to
  rerun a search.)
* Run outputs go to `runs/`, which is gitignored.

## 11. Limitations

* Besides the verbatim question, only a small hand-curated concept map drives
  expansion; natural-language questions can still give noisy
  results, especially on Crossref (which ranks by relevance over all works).
* Crossref-sourced records are verified against Crossref itself, which
  confirms that the DOI resolves and the metadata is consistent, but is not an
  independent cross-check. Records found in PubMed with a DOI are cross-checked
  against Crossref.
* Title matching is lexical; translated titles, Greek letters vs. spelled-out
  names, or heavy markup differences can produce `partially_verified`.
* Year semantics differ between sources. PubMed's `pdat` date filter matches
  the electronic *or* print publication date, while SciForge's PubMed `year`
  comes from esummary `pubdate` (usually the print/issue date). A search limited
  to 2020–2024 can therefore return a record whose `year` is 2025 (e-published
  2024, printed 2025). The same e-pub/print gap between Crossref `issued` and
  PubMed `pubdate` can make an otherwise correct record `partially_verified`
  with `doi:year_mismatch`. SciForge reports this rather than guessing which
  date is "right".
* First-author matching uses surnames only, parsed heuristically from
  `"Family, Given"` / `"Family AB"` / `"Given Family"` forms; compound or
  transliterated names may mismatch.
* Deduplication is intentionally conservative; some true duplicates without
  DOIs will remain separate.
* No abstracts, full text, preprint labelling, evidence extraction, or
  reports yet; no resume-after-failure; requests are sequential.
* Crossref `rows` and PubMed `retmax` are capped at 1000; only the first page
  of results is retrieved.
