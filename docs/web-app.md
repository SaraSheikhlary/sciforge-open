# SciForge web app (Milestone 1)

A Streamlit interface for SciForge: **SciForge — AI for Scientific Discovery**.

> **Status.** Demo Mode is complete and fully tested offline. **Live Mode is untested with a real xAI
> API key and has not been validated live.** It reuses the existing, unit-tested `XAIClient` and budget
> code, but no end-to-end run against the real API has been made. Do not rely on Live Mode output yet.

## Architecture

```
streamlit_app.py            thin UI: widgets, progress display, tabs (no scientific logic)
        │ calls
        ▼
app/sciforge/app_service.py application interface: input validation, mode selection, credential presence
        │                   check, temp run directory, progress events, result shaping, display privacy guard
        ├── Demo Mode ─► app/sciforge/demo_data.py  (SYNTHETIC records + scripted FakeModelClient + offline
        │                                            MockTransport serving the synthetic abstracts)
        └── Live Mode ─► sciforge.pipeline.run_investigation (v0.2: PubMed + Crossref, dedup, verification)
                         + sciforge.llm.xai.XAIClient with ModelSettings budgets
        ▼
sciforge.investigation_pipeline.run_model_investigation   (existing v0.3 pipeline, unchanged)
   source texts → question definition → evidence extraction + deterministic validation →
   research gaps → hypotheses → report (narrative + deterministic template, citations by code)
```

`run_web_investigation(request, progress=callback)` takes an `InvestigationRequest` (question, optional
start/end year, maximum sources, mode `demo`/`live`) and returns a `WebInvestigationResult`:

| Field | Contents |
|---|---|
| `status` | `ok`, `degraded` (no validated evidence), `budget_exhausted`, `model_auth_error`, `error`, `invalid_input`, `live_unavailable` (Live Mode requested while gated off, without credentials, or with sign-in required but not configured), `live_unauthorized` (sign-in required and the user is anonymous, has no verified email, or is not on the allowlist), `live_quota_exceeded` (the per-user Live usage limit is reached) |
| `sections` | The report sections A–J exactly as rendered by `sciforge.stages.report.build_report` |
| `evidence`, `conflicts` | Accepted evidence items (claim, verbatim quote, category, confidence, `[S#]` source ref) |
| `gaps`, `hypotheses` | Accepted research gaps (labelled inference) and candidate hypotheses (v0.4: label "Unvalidated, AI-generated hypothesis for further investigation", claim level, prediction, alternative, falsification test, critic/revision status, capped confidence) |
| `evidence_graph` | v0.4 deterministic Evidence-to-Hypothesis Graph (the run's `evidence_graph.json`; see `docs/v0.4-hypothesis-engine.md`) |
| `sources` | Citation lines from `render_citation` over the v0.2 records (`[S#]` cited, `R#` retrieved but not cited); unresolvable ids as `[UNRESOLVED CITATION: id]` |
| `sources` (cont.) | Every entry carries `source_status` (metadata-based: `peer-reviewed journal article`, `preprint`, `conference paper`, `book/chapter`, `unknown`); preprints are labelled PREPRINT in the citation. Demo records are `unknown` (synthetic, no type metadata) |
| `validation` | Report validation status, citation counts, issues, evidence/gap/hypothesis/paragraph accept/reject counts with reason codes, `claim_checks` (deterministic exact-quote / numeric-consistency / citation checks with pass/fail counts; `semantic_claim_check.status = "not implemented"`, `ran = false`), budget usage (output tokens, reasoning tokens, output-side tokens charged, xAI-reported cost or `unavailable`), privacy-guard summary |
| `limitations`, `notices`, `errors` | Human-readable text |

The UI shows eight progress steps (Defining question, Searching literature, Verifying sources, Extracting
evidence, Checking evidence, Identifying research gaps, Generating hypotheses, Building report) and eight
result tabs (Overview, Evidence, Conflicts, Research Gaps, Hypotheses, Evidence Graph, Sources, Validation).
The **Evidence Graph** tab renders a DOT string generated by `sciforge.evidence_graph.graph_to_dot` with
`st.graphviz_chart` (rendered client-side; no graphviz Python package or other new dependency), with distinct
edge colours/styles and a legend (supports green, contradicts red dashed and bidirectional, motivates orange,
addresses purple, tests grey dotted). Graphviz charts are not clickable in Streamlit, so navigation uses a node
selector (`node_options`); the details panel (`node_details`, pure functions, rendered as tables so no Markdown
is interpreted) shows: source → verified bibliographic record + its evidence; evidence → exact verified quote,
source, gaps, recorded contradictions; gap → motivating evidence and hypotheses addressing it; hypothesis →
evidence, alternative, prediction, falsification test, critic result, revision status and the warning. Progress for
model stages is taken from the stage of each model request; "Checking evidence (deterministic checks)" is
the deterministic validation that runs inside extraction (exact quotes, numbers/units, ids). Semantic
(model-based) claim checking is not implemented, and the UI and reports say so.

Input limits: question 10–2000 characters; years 1800–2100 with start ≤ end (both optional); maximum
sources 1–20. In Live Mode the maximum sources is the number of verified sources the deterministic
selection aims for and the model source limit (never above `SCIFORGE_MODEL_MAX_SOURCES`); each expanded query
still collects a larger candidate pool (`SCIFORGE_CANDIDATE_POOL_PER_QUERY`) before deduplication, abstract
enrichment, ranking, source policy and verification.

### Citations

Every citation shown in the UI comes from the deterministic renderer
(`sciforge.stages.report.render_citation` / `unresolved_marker`) applied to v0.2 records. The model only
ever sees opaque record ids; it cannot create or edit citations.

### Privacy

- Questions are not persisted. The pipelines write their normal run files to a fresh directory under the
  system temp directory (prefix `sciforge-web-`), never the repository, and that directory is deleted
  before the result is returned. The optional raw-rejected-output debug file is always disabled.
- Every displayed string passes `guard_display`: secret redaction (`sciforge.logging_utils.redact_text`
  with the configured key values), key-shaped tokens, filesystem paths, and any raw rejected model output
  (needles from `sciforge.output_guard.rejected_text_values`). The run directory is also checked with
  `sciforge.output_guard.find_leaks` before deletion; the count is shown on the Validation tab.
- Rejected model items are shown only as reason codes and counts.
- API keys and environment values are never displayed. The UI only reports *whether* Live Mode is
  enabled for the deployment and *whether* `XAI_API_KEY` and `XAI_MODEL` are configured.
- Unexpected errors are shown as a generic message with the exception type only; `.streamlit/config.toml`
  sets `client.showErrorDetails = "none"` so tracebacks and paths never reach the browser, and
  `browser.gatherUsageStats = false`.
- Streamlit keeps the latest result in the in-memory session state of the browser session only.

## Local startup

```bash
git clone https://github.com/SaraSheikhlary/sciforge-open.git
cd sciforge-open
python -m venv .venv && source .venv/bin/activate
pip install -e ".[web]"          # package + streamlit (add ,dev for pytest: ".[dev,web]")
streamlit run streamlit_app.py   # opens http://localhost:8501
```

`streamlit_app.py` also works from a plain checkout without installing the package (it adds `app/` to
the import path), as long as the dependencies are installed (`pip install -r requirements.txt`).

Tests (offline; network access is blocked by the test suite): `pytest -q` (UI tests use
`streamlit.testing.v1.AppTest`).

## Demo Mode (default)

Demo Mode needs no API key and no network. It runs the real v0.3 pipeline on a bundled, clearly labelled
**synthetic** example investigation (topic: study preregistration and reported effect sizes — the
metascience of the published literature):

- five synthetic v0.2-shaped records with DOIs `10.0000/demo.*` (an unassigned prefix), titles starting
  with `[SYNTHETIC DEMO]`, authors `Demo Author …`, journal "SciForge Synthetic Demo Journal (not a real
  journal)", and invented abstracts starting with `SYNTHETIC DEMO ABSTRACT`. Their verification statuses
  (three verified, one partially verified, one not verified) are assigned by the demo data, not checked;
- a scripted `FakeModelClient` that answers each stage from the ids in the request, so the deterministic
  checks run for real. One evidence item deliberately quotes text that is not in the abstract, so the
  Validation tab shows one `quote_not_in_source` rejection (its text is never displayed);
- abstracts are served through an `httpx.MockTransport` in Crossref `/works/{doi}` shape (no socket is
  opened).

Demo Mode always analyses the same dataset; the entered question is echoed in the question definition but
not searched. The year filter and maximum sources are applied to the synthetic records. The UI labels all
demo output as synthetic; none of it is a real finding.

## Live Mode (experimental, not validated live)

### Deployment gate

Live Mode needs an explicit opt-in per deployment:

| Condition | Live Mode |
|---|---|
| `SCIFORGE_LIVE_ENABLED` unset (default), empty, or any value other than `true` | **disabled** — "Live Mode is disabled for this deployment", whatever credentials exist |
| `SCIFORGE_LIVE_ENABLED=true` but `XAI_API_KEY` or `XAI_MODEL` missing/empty | **unavailable** — the missing names are listed (never values) |
| `SCIFORGE_LIVE_ENABLED=true` and both `XAI_API_KEY` and `XAI_MODEL` non-empty | enabled (experimental) |

Only the exact value `true` enables the gate (case-insensitive, surrounding whitespace ignored); `1`,
`yes`, `on`, and unquoted TOML booleans in `secrets.toml` all count as false. The gate is enforced twice:
the UI disables the Live option, and `run_web_investigation` itself refuses a live request
(`status = "live_unavailable"`) before creating a temp directory, calling PubMed/Crossref, or building
an `XAIClient`. The live runner checks again. Demo Mode ignores the gate and credentials completely.

### Sign-in and allowlist (public deployments)

On top of the gate, Live Mode requires sign-in unless `SCIFORGE_LIVE_REQUIRE_AUTH` is exactly `false`
(case-insensitive, trimmed). **Fail closed:** unset, blank, `0`, `no`, typos and unquoted TOML booleans all
mean sign-in is required. Sign-in uses Streamlit's native OIDC support (`st.login()`, `st.logout()`,
`st.user`), configured by an `[auth]` section in `.streamlit/secrets.toml` with `redirect_uri`,
`cookie_secret`, `client_id`, `client_secret` and `server_metadata_url` (see
`.streamlit/secrets.toml.example`; placeholders only). Streamlit's login needs the **`Authlib`** package,
which the `web` extra now lists (`Authlib>=1.3.2`); install it in the deployment.

`SCIFORGE_LIVE_ALLOWED_EMAILS` (environment or `st.secrets`; comma-separated string or TOML list; never
hard-coded) is matched case-insensitively after trimming, as an exact match against `st.user.email`.

| Situation (gate on, key and model set) | Live Mode |
|---|---|
| `SCIFORGE_LIVE_REQUIRE_AUTH=false` | available (gate + credentials only, as before) |
| sign-in required, `[auth]` incomplete or Authlib not installed | **unavailable** (`live_unavailable`) — fail closed |
| sign-in required, user not logged in | **unavailable**; a "Log in for Live Mode" button is shown |
| logged in, provider reports `email_verified = false`, or no email | **refused** (`live_unauthorized`) |
| logged in, email not on the allowlist (or allowlist empty) | **refused** (`live_unauthorized`) |
| logged in, email on the allowlist | available |

Demo Mode is always public and never asks for sign-in. The UI builds a `LiveIdentity` (only
`is_logged_in`, `email`, `email_verified`; identity-provider tokens are never read) from `st.user` and passes it
in `InvestigationRequest.identity`; `run_web_investigation` computes the access decision itself and refuses
before creating a temp directory, calling PubMed/Crossref, or building a model client; the live runner checks
again. Only the decision (`allowed` / `denied:<reason>`) is logged, never the email or any token. The email
is not displayed. The xAI key stays server-side. Note: the service trusts the identity object passed by the
server-side UI code (it cannot re-verify the OIDC session itself); the protection is against browser users,
not against code running on the server.

### Kill switch

`SCIFORGE_LIVE_KILL_SWITCH` (environment, then `st.secrets`) is checked first, in the UI availability check and
again in the service layer before any network activity. Parsing is fail-safe: unset, empty or exactly `false`
(case-insensitive; TOML `false`) means **off**; any other value (`true`, `1`, `yes`, `on`, a typo, ...) means
**on**, and Live Mode is unavailable regardless of the gate, credentials or sign-in. Demo Mode is unaffected.

### Per-user usage limit (sign-in required only)

| Setting | Default | Meaning |
|---|---|---|
| `SCIFORGE_LIVE_MAX_RUNS_PER_USER` | `3` | Live runs per signed-in user per rolling 24 h; integer 1-1000, anything else is a configuration error |
| `SCIFORGE_LIVE_QUOTA_PATH` | `$XDG_STATE_HOME/sciforge/live_quota.json`, else `~/.local/state/sciforge/live_quota.json` | Absolute path of the JSON store (outside the repo and run directories) |
| `SCIFORGE_LIVE_QUOTA_SALT` | unset | Secret key for HMAC-SHA256 of the email; unset = plain SHA-256 (guessable from candidate emails) |
| `SCIFORGE_LIVE_QUOTA_BACKEND` | `file` | `file` (local JSON store, single host) or `postgres` (shared database); anything else is a configuration error and Live Mode is unavailable |
| `SCIFORGE_LIVE_QUOTA_CONNECTION` | `sciforge_quota` | Name of the Streamlit SQL connection for `postgres` (`[connections.sciforge_quota]` in secrets); 1-64 letters, digits, `_`, `-` |

- Identity is only the verified email (trimmed, lower-cased); a missing or unverified email is refused.
- The store holds `{hash: [timestamps]}` only; the plaintext email is never written, logged or displayed.
- A run counts when an authorised Live run starts (after kill switch, gate, credentials, sign-in/allowlist and
  configuration checks; before literature lookup, temp directory or model client). Failed runs therefore count;
  refused runs do not. The 4th run inside 24 h is refused with `live_quota_exceeded`; Demo Mode stays available.
- The store is locked (`fcntl`) and written atomically; if it cannot be read or written, Live Mode is refused
  (fail closed). It is per host: use a persistent path, and note that several replicas or an ephemeral
  filesystem (e.g. a Streamlit Community Cloud restart) do not share or keep counts.
- With `SCIFORGE_LIVE_REQUIRE_AUTH=false` behaviour is unchanged: no quota (there is no verified identity).

#### Quota backends

Both backends implement one atomic operation, `check_and_record(identity_hash, now, limit, window_s)`
(`QuotaBackend` in `app/sciforge/live_quota.py`); only the identity hash and timestamps reach a backend.

- **`file`** (default; local development and single-host deployments): the JSON store above.
- **`postgres`** (`app/sciforge/live_quota_sql.py`; for multi-replica or ephemeral hosts such as Streamlit
  Community Cloud). Uses `st.connection("<SCIFORGE_LIVE_QUOTA_CONNECTION>", type="sql").engine` (SQLAlchemy).
  Database credentials live **only** in the `[connections.<name>]` secrets section; the SciForge service never
  receives them. Needs `SQLAlchemy` and `psycopg` (declared in the `web` extra).
  - **Schema:** apply `deploy/sql/001_live_quota.sql` once (idempotent `CREATE TABLE IF NOT EXISTS` /
    `CREATE INDEX IF NOT EXISTS`): table `sciforge_live_quota_events(id bigserial, identity_hash text,
    created_at timestamptz)` with an index on `(identity_hash, created_at)`. The app **never creates or alters
    tables**; a missing table is a database error, so Live Mode is refused until the migration is applied.
    Grant the app role only `SELECT, INSERT, DELETE` on the table and `USAGE` on its sequence.
  - **Atomicity:** one transaction per request: `SELECT pg_advisory_xact_lock(hashtext(:identity_hash))`
    (serialises requests of the same identity until commit), delete that identity's events older than the
    window, count the remaining events, insert a new event only if the count is below the limit, commit. With
    limit N and N+k simultaneous requests exactly N succeed.
  - **Time source:** the application clock (UTC, passed explicitly; the column default `now()` is unused), so
    keep replica clocks synchronised. Events dated slightly in the future are still counted (skew can only
    make the limit stricter).
  - **Fail closed:** `postgres` without a complete `[connections.<name>]` section (`url`, or `dialect` +
    `username` + `host`) or without SQLAlchemy/driver → Live Mode unavailable in the UI with a generic message
    (no connection details). Any connection, authentication, missing-table or SQL error at run time → the run is
    refused (`live_unavailable`) before any literature lookup, temp directory or xAI client. Errors are logged
    by exception type only.
  - Demo Mode never touches the quota backend or the database.

### What Live Mode does

Live Mode is disabled in the UI unless the gate is on **and** both `XAI_API_KEY` and `XAI_MODEL` are present. When enabled,
it runs v0.2 retrieval (expanded queries, a candidate pool of `SCIFORGE_CANDIDATE_POOL_PER_QUERY` records per
query and database, default 10), deduplication, bounded abstract enrichment (`SCIFORGE_ABSTRACT_ENRICHMENT_LIMIT`,
default 50), deterministic relevance/diversity selection, metadata-based source classification with the
source policy (`SCIFORGE_SOURCE_POLICY`, default `peer_reviewed_preferred`; the web app shows a notice when
fewer sources than requested remain and when preprints were cited) and verification with backfill, so that at most the selected "Maximum sources" (and `SCIFORGE_MODEL_MAX_SOURCES`) verified
records reach the model; and then the v0.3 pipeline with the existing
`XAIClient` (Responses API, `store=false`). All existing limits apply unchanged, read by
`ModelSettings.from_env`: `SCIFORGE_MODEL_MAX_ATTEMPTS`, `SCIFORGE_MODEL_MAX_SOURCES`,
`SCIFORGE_MODEL_MAX_INPUT_TOKENS` (default 200,000), `SCIFORGE_MODEL_MAX_OUTPUT_TOKENS` (default 2,000) and its
per-stage overrides `SCIFORGE_MODEL_MAX_OUTPUT_TOKENS_{QUESTION,EVIDENCE,GAPS,HYPOTHESES,REPORT}`,
`SCIFORGE_MODEL_REASONING_EFFORT` (default `high`) and its overrides
`SCIFORGE_MODEL_REASONING_EFFORT_{EVIDENCE,GAPS,HYPOTHESES,REPORT}`, `SCIFORGE_MAX_SPEND_USD` (web Live default
**2 USD** when unset — the CLI/library default stays 15; an explicit value, including `none`, is honoured; the
hard financial guard — the output-token settings are sent as `max_output_tokens` but are not a total token
ceiling, because xAI reports and bills reasoning tokens separately; output-side tokens are charged as output +
reasoning, and `cost_in_usd_ticks` is recorded as the actual cost when supplied; while the cap is on, `SCIFORGE_PRICE_INPUT_PER_MTOK` and `SCIFORGE_PRICE_OUTPUT_PER_MTOK` must be
set or Live Mode refuses to start — set `SCIFORGE_MAX_SPEND_USD=none` to disable the cap explicitly). See
`.env.example` for all variables. A budget stop or an authentication failure is reported as a status; the
remaining report sections are built by code only.

Live Mode has only been exercised in offline tests (mock HTTP transport and fake model). It has **not**
been run with a real key.

## Secret configuration

Order of precedence for `SCIFORGE_LIVE_KILL_SWITCH`, `SCIFORGE_LIVE_ENABLED`, `XAI_API_KEY`, `XAI_MODEL`,
`SCIFORGE_LIVE_REQUIRE_AUTH`, `SCIFORGE_LIVE_ALLOWED_EMAILS`, `SCIFORGE_LIVE_MAX_RUNS_PER_USER`,
`SCIFORGE_LIVE_QUOTA_PATH`, `SCIFORGE_LIVE_QUOTA_SALT`, `SCIFORGE_LIVE_QUOTA_BACKEND` and
`SCIFORGE_LIVE_QUOTA_CONNECTION` (the `[connections.<name>]` section is read only by Streamlit's
`st.connection`, and by the app for a presence check):

1. **Environment variables** (a non-empty value always wins; e.g. `SCIFORGE_LIVE_ENABLED=false` in the
   environment disables Live Mode even if secrets say `"true"`).
2. **Streamlit secrets** (`st.secrets`): `.streamlit/secrets.toml` locally, or the app's *Secrets*
   setting on Streamlit Community Cloud. Only these names (plus Streamlit's own `[auth]` section, checked
for presence only) are read from `st.secrets`. Write the gate
   as a quoted string: `SCIFORGE_LIVE_ENABLED = "true"`.

All other settings (budgets, prices, spend cap, `NCBI_API_KEY`, `SCIFORGE_CONTACT_EMAIL`) are read from
environment variables only.

Local secrets file: copy `.streamlit/secrets.toml.example` to `.streamlit/secrets.toml` (gitignored) and
fill in real values. Never commit it. The key is used only server-side in the `Authorization` header of
requests to the xAI API; it is never sent to the browser, logged, or displayed.

## Streamlit Community Cloud deployment

1. Push the repository to GitHub (the app needs `streamlit_app.py`, `requirements.txt`, `pyproject.toml`,
   `app/` and `.streamlit/config.toml`; never `.streamlit/secrets.toml`).
2. On <https://share.streamlit.io>, create an app from the repository, branch, and main file
   `streamlit_app.py`; choose Python 3.10 or newer.
3. `requirements.txt` installs the package from `app/` with the `web` extra (`.[web]`).
4. Demo Mode works with no further setup; Live Mode stays disabled by default (no `SCIFORGE_LIVE_ENABLED`).
5. Live Mode (optional, not yet validated live): in *App settings → Secrets* add
   `SCIFORGE_LIVE_ENABLED = "true"`, `XAI_API_KEY` and `XAI_MODEL`, plus either both price variables or
   `SCIFORGE_MAX_SPEND_USD = "none"`. Leave the gate out (or `"false"`) for a public demo-only deployment. Community Cloud
   also exports root-level secrets as environment variables, which is how the non-credential settings are
   read. Every Live Mode run spends from your xAI account, so keep sign-in on: add the `[auth]` section
   (register `https://<your-app>.streamlit.app/oauth2callback` as the redirect URI with your OIDC provider)
   and `SCIFORGE_LIVE_ALLOWED_EMAILS`; make sure `Authlib` is installed (it is in the `web` extra).
6. Community Cloud's filesystem is not persistent, so use the shared quota backend there:
   `SCIFORGE_LIVE_QUOTA_BACKEND = "postgres"`, a `[connections.sciforge_quota]` section (placeholders in
   `.streamlit/secrets.toml.example`; use `sslmode=require`), a `SCIFORGE_LIVE_QUOTA_SALT`, and apply
   `deploy/sql/001_live_quota.sql` to the database first.

## Limitations

- Live Mode is untested with a real xAI key; not validated live. It is off by default
  (`SCIFORGE_LIVE_ENABLED` must be `true`).
- Evidence comes from abstracts only; claims are checked deterministically only (exact quotes, numbers/units,
  ids and citations), not for scientific quality. Semantic (model-based) claim checking is not implemented.
- Source types are metadata-based; "peer-reviewed journal article" is not a guarantee of peer review.
- Demo Mode ignores the content of the entered question (fixed synthetic dataset).
- Progress for "Searching literature" and "Verifying sources" is reported when the v0.2 engine finishes
  (both happen inside one v0.2 call).
- The per-user limit (default 3 Live runs / rolling 24 h) with the `file` backend is per host and needs a
  persistent quota path; use the `postgres` backend for replicas/ephemeral hosts. The postgres backend is
  tested offline only (SQLite and a fake engine; no real PostgreSQL). There is no global per-day cap. `SCIFORGE_MAX_SPEND_USD` bounds spend per investigation; one attempt can
  exceed its worst-case estimate because reasoning is billed on top of `max_output_tokens`.
- Labels: Demo Mode = synthetic, offline (no real literature, no xAI); Live Mode = real literature + real xAI
  (costs money, sign-in required); "Preprint — not peer-reviewed"; deterministic validation = exact quote,
  numeric and citation checks; semantic claim entailment: not implemented. Hypotheses are unvalidated,
  AI-generated hypotheses for further investigation, not validated discoveries.
- When the server starts, Streamlit itself may look up the machine's external IP address to print URLs
  in the console; this is Streamlit behaviour, unrelated to SciForge or xAI.
